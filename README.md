# Hospital Management System (HMS)

> **College PAT 4 Practical Examination Project**  
> **Architecture:** Spring Boot &bull; Spring MVC &bull; Thymeleaf &bull; Spring JDBC / PreparedStatements &bull; Oracle FreeSQL &bull; Spring Security &bull; BCrypt

---

## 1. Project Overview

The **Hospital Management System** is an enterprise-grade full-stack web application engineered for the **PAT 4 Practical Examination**. It provides end-to-end management of hospital operations including patient registration, medical specialist scheduling, appointment bookings with 30-minute slot overlap conflict detection, transaction-aware concurrency controls, and real-time executive dashboard reporting.

All data persistence is handled exclusively through **pure Java JDBC (Spring `JdbcTemplate` / PreparedStatements)** connecting to an **Oracle FreeSQL** remote database. **No JPA, Hibernate, SQLite, H2, or simulated repositories are used**, strictly meeting all academic examination requirements.

## 3. Remote Oracle FreeSQL Database Schema

The system operates against the four existing relational tables in Oracle FreeSQL:

```
+---------------------------------------------------------------------------------+
|                                 APP_USERS                                       |
|  user_id (PK) | username (UQ) | password_hash | full_name | user_role | is_active |
+---------------------------------------------------------------------------------+

+---------------------------------------------------------------------------------+
|                                  PATIENTS                                       |
|  patient_id (PK) | full_name | date_of_birth | gender | phone | email | address |
+---------------------------------------------------------------------------------+
                                      | 1
                                      |
                                      | N
+---------------------------------------------------------------------------------+
|                                APPOINTMENTS                                     |
|  appointment_id (PK) | patient_id (FK) | doctor_id (FK) | appointment_datetime  |
|                      | reason          | status         | created_at            |
+---------------------------------------------------------------------------------+
                                      | N
                                      |
                                      | 1
+---------------------------------------------------------------------------------+
|                                  DOCTORS                                        |
|  doctor_id (PK) | full_name | specialization | phone | email | consultation_fee |
|                 | is_active                                                     |
+---------------------------------------------------------------------------------+
```

### Table Definitions:

1. **`APP_USERS`**:
   - `user_id`: `NUMBER GENERATED BY DEFAULT AS IDENTITY`, Primary Key.
   - `username`: `VARCHAR2(50)`, Unique and Not Null.
   - `password_hash`: `VARCHAR2(255)`, Not Null (BCrypt encoded).
   - `full_name`: `VARCHAR2(100)`, Not Null.
   - `user_role`: `VARCHAR2(20)`, Default `'RECEPTIONIST'` (Allowed: `ADMIN`, `RECEPTIONIST`, `DOCTOR`).
   - `is_active`: `CHAR(1)`, Default `'Y'` (Allowed: `'Y'`, `'N'`).
   - `created_at`: `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`.

2. **`PATIENTS`**:
   - `patient_id`: `NUMBER GENERATED BY DEFAULT AS IDENTITY`, Primary Key.
   - `full_name`: `VARCHAR2(100)`, Not Null.
   - `date_of_birth`: `DATE`.
   - `gender`: `VARCHAR2(20)`.
   - `phone`: `VARCHAR2(20)`, Not Null.
   - `email`: `VARCHAR2(120)`.
   - `address`: `VARCHAR2(300)`.
   - `created_at`: `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`.

3. **`DOCTORS`**:
   - `doctor_id`: `NUMBER GENERATED BY DEFAULT AS IDENTITY`, Primary Key.
   - `full_name`: `VARCHAR2(100)`, Not Null.
   - `specialization`: `VARCHAR2(100)`, Not Null.
   - `phone`: `VARCHAR2(20)`.
   - `email`: `VARCHAR2(120)`.
   - `consultation_fee`: `NUMBER(10,2)`, Default `0` (`CHECK (consultation_fee >= 0)`).
   - `is_active`: `CHAR(1)`, Default `'Y'` (`CHECK (is_active IN ('Y', 'N'))`).

4. **`APPOINTMENTS`**:
   - `appointment_id`: `NUMBER GENERATED BY DEFAULT AS IDENTITY`, Primary Key.
   - `patient_id`: `NUMBER`, Not Null (Foreign Key referencing `PATIENTS(patient_id)`).
   - `doctor_id`: `NUMBER`, Not Null (Foreign Key referencing `DOCTORS(doctor_id)`).
   - `appointment_datetime`: `TIMESTAMP`, Not Null.
   - `reason`: `VARCHAR2(500)`.
   - `status`: `VARCHAR2(20)`, Default `'SCHEDULED'` (Allowed: `SCHEDULED`, `COMPLETED`, `CANCELLED`, `NO_SHOW`).
   - `created_at`: `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`.

> **Note on DDL:** Full reference DDL statements and indexes are documented in `database/schema.sql`. The application **never executes DDL** or automated table drop/create against the live remote database (`spring.sql.init.mode=never`). Working sample DML scripts are provided in `database/dml_examples.sql`.

## 4. Key Functional Modules

### A. Login & Authentication
- Secure login portal at `/login` with credentials validation.
- Rejects invalid passwords and deactivated user accounts (`is_active = 'N'`).
- Role-based authorization (`ADMIN`, `RECEPTIONIST`, `DOCTOR`).
- Automatic CSRF protection on all state-changing HTTP POST requests.
- Server-side session invalidation on logout.

### B. Executive Dashboard (`/dashboard`)
- Real-time KPI summary cards powered by Oracle SQL aggregate queries:
  - Total Registered Patients (`SELECT COUNT(*) FROM PATIENTS`)
  - Active Available Doctors (`SELECT COUNT(*) FROM DOCTORS WHERE is_active = 'Y'`)
  - Total Appointments and Scheduled Slots breakdown.
- Upcoming appointments roster with patient contact and status badges.
- One-click navigation to core workflows.

### C. Patient Management (`/patients`)
- Register new patients with form validation (Name, Phone, Email, DOB, Gender, Address).
- Search patients by Patient ID (numeric), Full Name (case-insensitive `LIKE`), Phone, or Email.
- Detailed patient view displaying demographic profile and full appointment history.
- Edit existing patient information.
- Safe deletion handling: Checks child foreign key constraints (`SELECT COUNT(*) FROM APPOINTMENTS WHERE patient_id = ?`). Rejects hard deletion if appointments exist to protect referential integrity.

### D. Doctor Management (`/doctors`)
- Add new doctors with validation enforcing non-negative consultation fees (`>= 0`).
- Search and filter doctors by name, specialization, and availability status.
- Doctor consultation profile displaying consultation fee, contact info, and assigned appointments.
- Activation toggle: Instantly activate or deactivate doctors without deleting records.
- Inactive doctors are automatically prevented from receiving new bookings.

### E. Appointment Management & Concurrency Control (`/appointments`)
- Book appointments using database-backed dropdowns for existing patients and active doctors.
- **30-Minute Slot Conflict Prevention:** Computes `|appointment_datetime - targetTime| < 30 minutes` for the assigned doctor and prevents overlapping consultations.
- **Simultaneous Booking Concurrency Control:** Executes inside `@Transactional(isolation = Isolation.READ_COMMITTED)` and issues a pessimistic row lock:
  ```sql
  SELECT doctor_id, is_active FROM DOCTORS WHERE doctor_id = ? FOR UPDATE;
  ```
  Any simultaneous booking attempt for the same doctor must serialize, eliminating race conditions.
- Reschedule appointments with slot validation.
- Status updates: Mark appointments as `COMPLETED`, `CANCELLED`, or `NO_SHOW`.

### F. Search & Daily Reporting (`/appointments/report`)
- Filter appointments by doctor, patient, status, and custom date range.
- **Daily Clinical Report:** Select any calendar day (default: Today) to view:
  - Total appointments scheduled for the day.
  - Completed appointments count.
  - Calculated revenue from completed consultations (`SUM(d.consultation_fee)`).
  - Print-ready stylesheet formatted for physical printer or PDF export.

### G. User Management (`/users` - Admin Only)
- View all system user accounts in `APP_USERS`.
- Provision new staff accounts (`RECEPTIONIST`, `DOCTOR`, `ADMIN`) with BCrypt hashed passwords.
- Deactivate/activate accounts.

## 5. Safe Administrator Bootstrap

The application contains an automatic, idempotent bootstrap mechanism (`AdminBootstrapService`):
1. On application startup, it queries `SELECT COUNT(*) FROM APP_USERS`.
2. **If and only if `APP_USERS` is completely empty (0 records)**, it creates an initial administrator account using `APP_BOOTSTRAP_USERNAME` (default `admin`) and `APP_BOOTSTRAP_PASSWORD` (default `Admin@123`).
3. The password is encrypted with `BCryptPasswordEncoder` prior to storage.
4. If one or more user accounts already exist, the bootstrap is skipped and no existing passwords or accounts are touched.

## 8. Viva & Examination Concepts (PAT 4 CSE Guide)

When presenting this project during your practical examination, explain the following key database and full-stack concepts:

### 1. DDL & Schema Constraints
- **Identity Columns:** `NUMBER GENERATED BY DEFAULT AS IDENTITY` automatically generates sequential surrogate primary keys in Oracle without requiring explicit sequences or triggers.
- **Foreign Keys:** `FOREIGN KEY (patient_id) REFERENCES PATIENTS(patient_id)` guarantees referential integrity.
- **Check Constraints:** `CHECK (consultation_fee >= 0)` and `CHECK (user_role IN ('ADMIN', 'RECEPTIONIST', 'DOCTOR'))` enforce data domain rules directly at the database engine level.

### 2. JDBC & SQL Injection Prevention
- All database queries use `PreparedStatement` parameter placeholders (`?`).
- Parameter binding ensures user inputs are sent separately from SQL syntax, completely neutralizing SQL Injection attacks.

### 3. Concurrency Control & Row-Level Locking (`FOR UPDATE`)
- In `AppointmentService.bookAppointment()`:
  - We acquire an exclusive pessimistic row lock: `SELECT ... FROM DOCTORS WHERE doctor_id = ? FOR UPDATE;`
  - In Oracle, this locks only the specific doctor's record within the transaction.
  - If two receptionists attempt to book the same doctor at the same moment, the second transaction is held in a wait state until the first completes.
  - This guarantees that two overlapping 30-minute appointments can never be double-booked.

### 4. Mathematical Overlap Logic (30-Minute Windows)
- Two consultation intervals `[T1, T1 + 30)` and `[T2, T2 + 30)` overlap if and only if `|T1 - T2| < 30 minutes`.
- In SQL:
  ```sql
  WHERE doctor_id = ? 
    AND status != 'CANCELLED'
    AND appointment_datetime > (target_time - INTERVAL '30' MINUTE)
    AND appointment_datetime < (target_time + INTERVAL '30' MINUTE)
  ```

### 5. ACID Transactions (`@Transactional`)
- Multi-step operations (locking, overlap checking, and inserting) execute inside a single database transaction. If any validation fails, Spring automatically triggers a `ROLLBACK`, preserving database consistency.

### 6. Referential Integrity in Deletion
- Before deleting a patient (`DELETE FROM PATIENTS`), the service queries `SELECT COUNT(*) FROM APPOINTMENTS WHERE patient_id = ?`.
- If child records exist, it rejects the deletion gracefully and notifies the user, preventing unhandled `ORA-02292: integrity constraint violated` errors.

### 7. Authentication & BCrypt Cryptography
- Passwords are never stored in plain text. They are hashed using BCrypt, an adaptive salt-based cryptographic algorithm resistant to rainbow table and brute-force attacks.
